# T0 Baseline Regression Audit

## Scope and reference

Baseline production revision: `3a2b6a0d4f862eaf3599fe910851c23116e59001`.
Completed implementation reference: `42c3d18cd2b2a727f0d6bb0e88f0115ef0bc8108`.
See [the review plan](checkpoint_2_review_plan.md) for preservation details and
the S1 through S5 implementation sequence.

T0 changes tests, their BUILD dependencies, fixtures, and review documentation.
It does not change compiler or runtime production code. It adds 22 real
Define-source projects and extracts their complete graph assertions, along with
expectations imported from the completed implementation in existing graph tests.

The failure audit below classifies differences from the baseline; it is not an
independent derivation of every expectation from the specification. The separate
[rule-by-rule specification audit](checkpoint_2_specification_audit.md) reviewed
all 97 modified existing graph tests: 75 have supported expectations, and 22
depend on a destructor-ordering rule absent from the specification. Those 22
expectations remain unresolved. No graph expectation was regenerated from the
baseline compiler, but that alone does not establish its correctness.

## Baseline and extraction checks

- The untouched baseline passed all 354 repository test targets.
- Baseline regeneration completed for 347 ordinary codegen cases and 132 tracing
  cases, including 27 newly registered tracing fixtures. Their 315 traced Python
  files and 27 dependency expectations are generated by the baseline compiler,
  not copied from the completed implementation. Existing generated artifacts are
  unchanged.
- The first unsuppressed graph audit produced 114 failures. All reached the
  dependency comparison or transitive-minimality assertion; none were missing
  fixtures, diagnostic errors, or unavailable test APIs.
- One failure was solely the completed implementation's changed diagnostic
  labels in the independent diamond case. T0 retains the baseline's existing
  diamond labels instead. That case needs no expected-failure marker.
- The remaining 113 graph failures have case-specific strict markers restricted
  to `AssertionError`. Their planned fixes and observations are listed below.
- Nine new callee-independence parameter cases initially passed without markers.
  Repeated concurrency checks exposed the races recorded below.
- All 27 source scenarios now use the existing fixture-driven tracing tests;
  none was already registered in that suite. The separate cross-action test and
  the five two-order initialization tests were removed during review. Internal
  initialization order is not an implementation-independent requirement.
- The existing tracing tests check generated artifacts, direct-dependency
  uniqueness, runtime scheduling tables, and concurrent dependency
  relationships. Eight new cases have audited scheduling-table mismatch markers;
  three of those also fail the concurrent dependency-relationship check. Passing
  either comparison does not prove the baseline graph is correct; the
  independent graph assertions remain necessary.
- Two new runtime Guarantee tests and one tracing dependency test are adapted to
  the baseline API rather than waiting for the mechanical Fanout rename.
  Existing runtime and Destruction Connection tests remain intact.

## Initialization race and deferred checks

The multi-worker audit exposed an initialization race in the baseline:
`MiddleExecution.execution_global_position_parent__action_destroyer` is used
before the execution exists. It appeared in
`caller_configures_multiple_destroys_after_independent_inits` with traced
execution and in repeated ordinary execution of
`caller_configures_destructor_after_independent_inits`,
`contributed_destructor_calls_action_with_child_destruction`, and
`contributed_destructor_move_removes_fill_after_two_destruction_dependencies`.

Repeated concurrent validation also reproduced the same race in traced
`caller_configures_only_destructor_after_independent_inits`.

These are intermittent failures, so the five affected projects have non-strict
xfail markers in ordinary execution and the existing concurrent tracing test.
They still run with the normal concurrent worker configuration. The first
repository-wide coverage attempt reproduced the same missing-execution race in
two new callee-independence variants after removing the additional Destructor:
`caller_configures_multiple_destroys_after_independent_inits` and
`contributed_destructor_move_removes_fill_after_two_destruction_dependencies`.
Repeated validation reproduced it in the
`caller_configures_destructor_after_independent_inits` variant too. Those three
variants also have non-strict xfail markers and retain concurrent execution. The
single-worker workarounds initially introduced during T0 were removed following
review. The separate tests asserting initialization order were subsequently
removed. Existing tracing tests retain their worker configuration: concurrent
execution for dependency relationships, and one worker for deterministic trace
artifact and direct-dependency checks.

S4/S5 must fix the race, remove these markers, and validate multi-worker
execution repeatedly. T0's tracing artifacts record baseline behavior, including
its known defects; independent graph assertions and expected-failure markers
record the required corrections. The completed implementation's tracing
artifacts remain in the reference snapshot for comparison during S5.

The new `test_propagated_destroy_uses_its_fragment_name` and adaptations of
existing naming tests depend on the redesigned Action Plan and remain with S5.
Changes that only reorder diagnostic expectations or Action Call Graph edges to
match a new compiler traversal also remain with the implementation. The
baseline's existing assertions are not removed for convenience.
