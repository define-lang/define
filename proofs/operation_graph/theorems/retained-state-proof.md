# Vacancy Selection and Shared Retained State

## Scope

This argument supplies the destruction-specific separation used by the
[candidate requirement construction](requirement-construction.md). The current
specification's graph calculation is not a premise. The semantic premises are
Simultaneous Transitive Destruction, the definition of a Vacate vertex,
Destructors and Destruction Ordering, Destructor Action Guarantees, and the
position-reference rules.

There are three different things to preserve:

1. The ordinary occupancy that a vacancy makes available for reuse.
2. The selected original particle and position described by that vacancy.
3. The changing original particle state used by destructors.

The second is fixed by selection. The third is shared and mutable, not a
separate snapshot for each destructor. Confusing either one with the first
reintroduces the incorrect assumption that a vacancy must wait for all retained
uses of the original particle.

## Selection is not a runtime barrier

Each source destruction determines selected particles from one logical preceding
state. Its individual Vacates denote their selected vacancies. The specification
explicitly excludes selecting replacement particles after another Vacate has
executed.

The occupied-state setter at each selected position is a requirement of that
individual vacancy. A Create or a Move into that position supplies its particle.
Moving a defining ancestor instead moves the selected position; it does not
supply new occupancy relative to its defining particle. The distinction matters
for implicit child Vacates, which have no newly written caller reference.

This is not a requirement to finish every selected particle's creation before
any vacancy in the group. The parent vacancy in the earlier constructor example
need not wait for the directly implied leaf Create. The leaf vacancy does. A
model that first executes a runtime traversal of the entire selected subtree
would introduce a group barrier not present in the required graph.

The additional Vacates generated for transitive children do not have newly
written references through every selected ancestor. Making their selections
ordinary reads would force an ancestor vacancy to wait for a child Vacate even
though both selections come from the same logical state. Each member retains its
selection rather than requiring the preceding vacancies to leave that state
intact.

The Vacate of the actual statement target is different: its written reference
still has the occupancy requirements imposed by Position References. Its strict
intermediate positions are outside the selected destruction. For instance,
`destroy ... parent::/child` reads `parent`, whereas the implicit child Vacate
generated by `destroy ... parent` does not separately read it. Saving the
selected particle does not waive the requirements of the written reference.

## Which state is shared

Before destruction, an ordinary operation accesses the actual particle and
position state. The initial retained state is that same original state, not
fresh particles. A retained operation can invalidate a preceding ordinary use of
an original occupied position: for example, a destructor Move can take its
particle away before a preceding ordinary Move has used it. Keeping the particle
alive does not make both sources occupied.

Thus retained calculation must inherit both the setters and the preceding uses
of its initial occupancy records. A retained read waits for its setter; a
retained Move that ends the occupancy additionally waits for those uses.
Subsequent retained operations share the updated records across destructors in
the chosen serial reference order. The ordinary vacancy itself does not empty
these retained records or make a retained Move wait for it.

This inheritance has two distinct effects. It prevents a destructor from using
the wrong pre-destruction state, and it prevents the destructor from changing an
original state before an earlier ordinary operation has used it. Merely copying
the preceding occupancy values without the earlier uses would not establish
either-direction scheduling correspondence.

## Why replacements do not share the original retained occupancy

Suppose a selected particle `P` defines a position `q`. After the caller's
destruction, a source reference that obtains a new particle at `P`'s former
position obtains that replacement's qualities and positions, not the originals.
The same spatial location does not identify the retained original occupancy with
the replacement's occupancy.

The ordinary caller cannot instead reach `P`'s original `q` through the
replacement. Nor do the position-reference rules give the caller an arbitrary
independent reference to `P`. Original accesses by already-triggered actions and
destructors must be represented as their actual references; they are not new
traversals through the replacement.

There is a different case when the particle defining the vacated position is not
selected. Destroying `Q` at `P`'s `q` leaves `P` as the defining particle, so
ordinary reuse of `q` follows its vacancy. A destructor assigned to `Q` directly
accesses qualities and positions of `Q`, not the inbound position `P`'s `q`
through which the caller formerly reached `Q`. Its own local positions are
likewise not that inbound position. Thus retaining `Q` and its defined positions
does not keep the caller's `q` occupied.

If a destructor calls other actions, their actual interface and implied
references preserve this distinction. They do not acquire an unrestricted
reference to the caller's surviving defining particle. Private local positions
cannot be reached by a different execution through an ordinary chained name.
These are reference restrictions, not an assumption that each destructor has
private copies of the selected particles.

## Nested destruction

A destructor can create a new particle and subsequently destroy it, for example
in a local position or in an initially empty contracted position that it must
restore to empty. Apply selection in the current state of that execution. Its
initial state may itself be retained state from an earlier destruction.

The same distinction applies recursively: the newly selected particle and its
positions remain available to its destructors, while the position in which it
was destroyed becomes reusable in the current execution. If that position's
defining particle was not selected by this nested destruction, its identity does
not change. Do not treat all uses after any destruction as belonging to one
undifferentiated retained copy.

For example, a destructor on `P` can Create a temporary particle in an initially
empty implied `/temporary`, Vacate it, then Create another there before
restoring `/temporary` to empty. The first temporary particle's Vacate must
precede the second Create: `P` is not selected by that new destruction, so the
same `/temporary` is being reused. The fact that these operations execute during
`P`'s destruction does not waive their vacancy dependency.

Destructor Action Guarantees also prevent treating destruction followed by
creation as restoration of an originally occupied contracted position. The
required original identity would have been lost. Newly created temporary
particles and retained original particles must remain distinct in this case as
well.

## A constructor and a retained ancestor Move

Let `P` define `/child`, occupied by `Q`. A constructor required by `/child`
implies `/leaf` and Creates `R` there. A destructor assigned to `P` implies
`/child` and Moves `Q` to its private local position `held`, then back. The
caller's subsequent destruction selects `P`, `Q`, and `R`. In the serial
reference execution the leaf Create occurs before this destruction and the two
destructor Moves.

The leaf Create requires `Q`, its `/leaf` quality, and an empty `/leaf`. The
first destructor Move requires its selected `Q` in the original `/child` and an
empty `held`. It does not fill or empty `/leaf`. Conversely, the Create does not
fill or empty `/child` or `held`. A destructor runs as an ordinary action, so
its Move has the same spatial semantics as the Move in the already proved
constructor exchange. The first Move and leaf Create can therefore exchange once
their respective setters and earlier conflicting uses have completed.

For example, the first Move may move `Q` and its empty `/leaf` to `held`; the
constructor can then create `R` in that position relative to `Q`. The return
Move moves `Q`, `/leaf`, and `R` back. This creates the same particle in the
same position defined by `Q` and preserves both Moves' actual endpoint
requirements. It does not require an uncreated `R` to participate in the first
Move. The transitive interaction of the return Move does include `R`.

The individual vacancy for `R` still follows its Create. It uses the recorded
selection from the caller's destruction, not a fresh evaluation of a name
through the destructor's now-empty `/child`. Selection is a logical-source
selection, not a claim that all selected particles coexisted at one runtime
instant before any vacancy or destructor operation. Requiring that runtime
instant would contradict the already established parent-destruction/leaf-Create
exchange.

Under the [Vanish rules](vanishment-proof.md), transitive movement alone does
not extend `R`'s lifetime. After `R`'s own Vacate and any actual uses of `R`, it
may Vanish before the return Move. The Move still requires `Q` and its actual
references. This changes no dependency between the Vacate and the return Move.

## An implicit child vacancy and an ordinary ancestor Move

Let `P` occupy `source` and define `/child`, occupied by `Q`. The caller Moves
`P` to `destination` and then destroys `destination`, selecting both particles.
Assume no destructors for this exchange. Write `M` for the Move, `DP` for the
written target's Vacate, and `DQ` for its implicit child Vacate.

`DP` requires occupancy at `destination`, supplied by `M`. `DQ` instead selects
the position `/child` defined by `P` and its original occupant `Q`. It has no
written reference through `destination`. After `Q`'s creation, `DQ` can vacate
that selected child position before `M`: the Move then moves `P` and its empty
`/child` position to `destination`. Executing `M` first instead moves the
occupied child position, after which `DQ` vacates it. Both orders execute the
same Move and selected vacancy and leave the same positions empty or occupied.
`DP` can then vacate `destination` in either order. No replacement is selected,
and no two ordinary particles occupy the same position.

The spatial location of the child vacancy differs between the orders, just as
the spatial location of an implied constructor Create can differ across a Move.
Its selected position defined by `P` is the same moving position. Giving `DQ`
the displayed name `destination::/child` does not create a written reference
with that chain. Conversely, actually writing a Destroy Particle Statement with
`destination::/child` does impose that reference and requires `M` first.

This is not permission to Vacate at a Move's empty destination. If the Move
transfers `Q` itself into the selected `/child` position, it supplies that
position's occupancy and must precede `DQ`. Moving the position's defining
particle is different from moving a particle into that position.

Discovery of a simultaneous selection does not make every discovery path an
actual Position Reference. The
[shared accessibility argument](#accessibility-during-shared-state-changes)
extends this distinction to retained destructor state.

## Representing the shared state without per-destructor copies

Fix a position `q` defined by a particle `P` selected for destruction.
Distinguish two observations of this original position: its vacancy for ordinary
code, and its changing occupancy for destructors using the original `P`. These
are not two spatial positions or two copies of their particles. The vacancy is
the selected ordinary effect; the changing retained occupancy is the original
particle state on which the destructors act.

Use one ordinary occupancy component and one retained component for this
mathematical representation. Every destructor accessing `P`'s original `q` uses
the same retained component. The ordinary selected vacancy does not empty it. A
Move by any of those destructors does change it. For a selected particle whose
defining particle is not in the same destruction, no retained component is
needed for its inbound position: its own destructors cannot obtain that position
through the assigned particle. Its ordinary vacancy empties that inbound
position as usual.

The distinction is per original position, not per destructor or per ancestor
through which selection was discovered. If `P` defines several positions, they
have separate occupancies. If another particle defines a child position, that
position belongs to that other particle. A Move of `P` does not write all those
components; their spatial movement follows from moving their defining particles.

### Supplying the initial retained value

The serial state immediately before destruction determines the initial value of
the retained component. Attribute that value to the last occurrence that
supplies the corresponding ordinary state, or to the position's initial state if
it has not been operated on. This is a value supplied by an existing occurrence,
not a runtime copying operation at the group of Vacates.

For example, a delayed constructor Create in `q` supplies both its ordinary
occupancy and the initial retained occupancy needed by a subsequent destructor.
The parent's vacancy need not wait for it. A destructor that actually uses
occupied `q` does wait for it. If an earlier temporary particle was destroyed
there and `q` is empty at the group, its vacancy instead supplies the empty
state needed by a destructor Create. No rule initializes the retained state
prematurely by inspecting an incomplete runtime prefix.

### Preserving preceding ordinary uses

Every ordinary operation that uses the final occupied state of `q` before the
destruction must also precede a retained operation that changes that state. For
the mathematical representation, give that use a requirement on the same initial
retained occupancy as well as its ordinary reference requirement. The two
requirements describe its access to the same original particle, not two
independent observations in the language.

The two components need not agree until the first retained change: the vacancy
can already have emptied ordinary occupancy while retained occupancy still gives
the original particle. The invariant needed for an ordinary use is narrower.
After the final setter and while such a use remains pending, neither the vacancy
nor a retained operation ending that occupied state can have occurred. Both
follow that use. Consequently the ordinary use still observes the actual
original occupancy, not a saved value that has ceased to describe its position.

After either the vacancy or a retained change, all these preceding ordinary uses
have finished. A still-pending vacancy uses the saved selection rather than a
fresh lookup in changed retained state. Subsequent destructor operations use the
shared changing original state. The ordinary and retained components may now
disagree without licensing an ordinary reference to a particle which a
destructor has moved away.

This invariant has a direct induction over the respecting schedule. Before the
final setter, its dependent uses cannot execute. After supply, reads leave the
occupied state unchanged. The vacancy and the first retained change each wait
for every ordinary use of that state, so neither can invalidate a pending use.
Later retained changes follow their own preceding setters and users. This covers
both orders of vacancy and retained change without imposing an edge between
them.

There are no read-only empty-position requirements from Particle Operations:
Create and Move destination require empty and immediately fill it. Accordingly,
an initially empty retained component needs its empty-state setter, not an
invented collection of empty-position readers.

This derives the candidate's inherited setter and reader dependencies. It also
explains why neither a whole-group copying barrier nor an edge between each
vacancy and each retained use is needed.

### Reuse and further destruction

After destruction, ordinary code cannot reach an original defined position
through a replacement for `P`: it reaches the replacement's qualities and
positions. When `P` survives destruction of a particle at `q`, ordinary reuse
instead uses that same `q` after its vacancy. The destroyed particle's own
destructors cannot access the surviving `P`'s inbound `q`. These are precisely
the two cases proved in the replacement argument above; neither gives ordinary
code access to a private retained copy.

Apply the construction again for particles created and destroyed during a
destructor. The current occupancy can already be a retained component from an
earlier destruction. The newly destroyed particles and their defined positions
are different original objects, not another independent copy of the earlier
ones. A valid serial execution cannot destroy the same original particle twice:
the first destruction removes it from ordinary access, and a destructor cannot
destroy and recreate an originally occupied contracted particle while satisfying
its unchanged identity guarantee.

This supplies an inductive decomposition by destruction, without imposing a
runtime order between their independent operations. It does not require copying
every transitive child's state at every ancestor.

## Accessibility during shared-state changes

The ordinary [reference-shape argument](reference-shape-proof.md) uses an
auxiliary acyclic accessibility representation with one incoming occupancy
association per particle. It cannot simply be applied to the union of the
ordinary and retained components: after a destructor Move, an ordinary saved
selection can still identify a particle which now occupies a different retained
position. Treating both observations as current occupancy would give that
particle two incoming associations.

Instead use one current occupancy association for each original position when
checking actual reference accessibility. Before the initial retained setter, use
its ordinary changing occupancy. After that setter, use the shared original
occupancy, including changes made by destructors. The setter gives the same
particle or empty state in both representations at this transition; there is no
copying step or added runtime operation. Ordinary vacancy is separately recorded
as the unavailability of its selected occupancy to ordinary references.

This representation agrees with every actual reference that is enabled by the
calculation:

- Before the final setter, subsequent retained accesses cannot execute. The
  ordinary reference argument applies.
- After the setter, an ordinary use of that final occupied state follows the
  setter and precedes both its vacancy and every retained change ending the
  state. The preceding-use invariant therefore gives exactly the original
  occupancy needed by that reference.
- A retained reference uses the one shared changing occupancy. Its actual
  intermediate positions, not the saved selection of a vacancy, determine its
  path.
- An ordinary reference following destruction cannot obtain an original defined
  position through a replacement. It obtains the replacement's positions. When
  the defining particle survives, the inbound position remains ordinary and its
  actual vacancy permits reuse, as proved above.

Retained access through a selected original parent and ordinary access through
its replacement therefore do not become two incoming associations to the same
particle. They involve different particles. An old selected vacancy is not a
second current access path at all.

The acyclicity induction can now be extended without assuming that saved
occupancy is current occupancy. A Create adds its fresh particle to one empty
position. A Move replaces its particle's one incoming occupancy association, and
its actual references satisfy the ordinary reference-shape argument in this
shared representation. Private declarations of destructor executions have the
same scope restrictions as those of other actions. Thus a Move cannot obtain an
otherwise inaccessible ancestor and place it in a position that it defines. This
reasoning applies to ordinary and destructor Moves, including their
interleavings.

A vacancy at a position whose defining particle survives removes that current
incoming association. The selected particle and its defined positions remain
available to its own destruction work, but its former inbound position is not
accessible through that particle. A vacancy whose defining particle is selected
instead leaves the original association available to the destruction work and
invalidates its ordinary observation. Neither case adds an association or a
cycle. A vacancy does not undo a preceding destructor Move by restoring the old
selected association. Further destructions apply these same cases to the current
originals, not to a new copy of an earlier destruction's state.

This is an accessibility argument, not a claim that detached particles still
occupy ordinary positions. The retained associations express the specification's
permission to operate on the originals as though in their preceding positions,
with subsequent destructor changes shared. Spatial movement still follows the
actual defining particles and current occupancy used by the operation, not every
ordinary selection record kept for a pending vacancy. In particular, an ordinary
ancestor Move does not pull a particle back out of a destructor's private local
position merely because an old selection records its former position.

Consequently the relative-occupancy exchange preserves geometric validity for
mixed operations as well as for ordinary operations. Its use of the ordinary
reference-shape argument is justified by the shared accessibility invariant, not
by assuming that two independent copies of particle state both describe physical
occupancy.

## Scheduling consequence

The representation above derives which observations must be shared and which are
separated by vacancy. The [scheduling proof](requirement-scheduling-proof.md)
applies the ordinary exchange argument to these shared components, checks
selected vacancies separately, and checks each retained cover edge for an actual
source-level obstruction to reversal. A failure caused only by an uninitialized
mathematical component does not suffice: its supplying occurrence must be
necessary for the particle or occupancy that the source operation needs.

## Checked component construction

For one original position, the component construction has seven cases. The last
ordinary fill or emptying supplies the same occupied-to-empty or
empty-to-occupied change to both its ordinary observation and its initial
retained observation. An ordinary use requires both to identify its selected
particle. Vacancy requires and empties only the ordinary observation. A retained
use, fill, or emptying requires and changes only the retained observation as
appropriate.

Three additional cases cover ordinary uses, fills, and emptyings before that
final setter, or at positions which have no retained occupancy. They observe and
change only ordinary occupancy. In particular, an earlier ordinary use must not
acquire a requirement on a retained observation initialized for a later
occupancy of the same position. Unmentioned positions have no requirement or
change from that operation.

Initialize the retained observation to the setter's preceding occupancy, not to
an invented unavailable value. If there is no occupancy setter, the initial
position is empty and the defining particle's existence is checked separately.
No earlier ordinary operation uses the retained observation. Subsequent retained
uses wait for the setter through Collection, so this mathematical initialization
cannot supply a particle or vacancy early. The setter's change is a real source
occupancy change in both observations.

These cases describe components of Particle Operations, not additional language
operations. A Move combines its source emptying, destination filling, and
reference uses into one effect. Simultaneous vacancy does not combine its peers
into one effect. The reference and preceding-use arguments above justify which
observation each actual operation uses; the component model alone does not
supply those semantic facts.

For all positions mentioned by one Particle Operation, take these component
requirements conjunctively and perform their changes together. Positions not
mentioned by it are unchanged. This is a product of component state spaces, not
an expansion into separately schedulable vertices. The whole effect is valid
because each changed component has its genuine required preceding value. Its
enabledness is exactly the conjunction of component enabledness, and its state
transition agrees at every component with the corresponding source change.
Induction over a schedule therefore transfers executions in both directions. The
graph scheduling and edge-necessity results apply to these whole effects; they
do not rely on an assumed independence between destructor executions.
