# Define Language Proposal X: Contract Files

- **Author:** Max Kanat-Alexander
- **Status:** Draft
- **Date Proposed:**
- **Date Finalized:**

## Problems

### 1: Inferred Contracts Are Invisible

[DLP 37 (Automatic Position Presence Constraints)](../define/proposals/00037-automatic-position-presence-constraints.md)
infers every action's Action Requirements and Action Guarantees from its Action
Statements Block. For the action's own statements, that inference is obvious
from reading the action.

It is not obvious for implied qualities. Requirements on implied positions
propagate transitively up the call chain from callees, and a callee's Guarantees
on implied positions apply to its callers. Reading an action does not show the
requirements it inherits from its callees, or the state its callees leave
behind. To learn them, a reader must follow every callee and repeat the
compiler's depth-first post-order traversal in their head.

This matters most for AI agents. They work with a few files at a time, and they
reliably get that traversal wrong. Today the only way for an agent to learn an
action's contract is to write a call and read the resulting errors, one error
per missing requirement.

### 2: Contracts Cannot Be Declared in Source

The obvious fix for problem 1 is syntax for declaring requirements and
guarantees in source. That syntax could cover interface positions and the
qualities an action names in its own Quality Implication Statements. It cannot
cover requirements on transitively implied qualities: under
[No Transitive References](../define/spec/spec.md#no-transitive-references), a
caller may not write the names those requirements are about. Declared contracts
would therefore work for one kind of contracted position and not the other.

### 3: Every Compilation Re-Infers Every Contract

The compiler computes each action's contract in a post-order traversal of the
reference graph, and each caller depends on its callees' contracts. The compiler
has no intermediate representation of those contracts, so every compilation
re-infers every contract, even when only one source file changed. A build system
also cannot tell that a callee's body changed while its contract stayed the
same, so it cannot avoid recompiling the callers.

## Solution

For every source file that defines an action, the compiler produces a **Contract
File** containing that action's inferred contract. A Contract File has two forms
with a single schema:

- A **text form** in the [Define Configuration Language](../defcl/spec/spec.md),
  for agents and people.
- A **binary form** in the protocol buffers wire format, for the compiler.

Each Contract File covers exactly one source file. Under
[Names Must Match Paths](../define/spec/spec.md#names-must-match-paths), a
source file defines at most one action, so each Contract File contains at most
one Action Contract. The compiler produces no Contract File for a source file
that defines no action.

### The Text Form

The text form of the Contract File for `handshake.dfn` is
`handshake.contract.defcl`, in the same directory. It is checked into version
control.

- Agents and people discover it by listing the directory, and read it like any
  other file.
- It begins with a comment that names the action, says the file is generated by
  the compiler, and gives the command that regenerates it.
- The compiler never reads it. Nothing the compiler does depends on its
  contents.
- A check mode of the compiler regenerates every text Contract File and fails if
  any checked-in file differs. Projects run this check in continuous
  integration, so the text Contract Files on a project's main branch always
  match the source.

### The Binary Form

The binary form is a local build artifact and is never checked in.

- When compiling a caller, the compiler reads the binary Contract Files of the
  caller's direct callees instead of re-inferring those contracts.
- A build system can use each binary Contract File as the input that callers
  depend on. When an edit to a callee leaves its binary Contract File
  byte-identical, callers do not need to be recompiled.
- One compiler build writes every binary Contract File in a build, so protocol
  buffers' lack of a byte-level canonical encoding does not affect this. A new
  compiler or protobuf library version causes one full rebuild.

### What a Contract File Contains

A Contract File contains only facts about the action's contract. It contains:

- No source locations. Adding a comment or blank line to a source file must not
  change its Contract File, or its callers would be recompiled.
- No digests, cache keys, or machine-specific data. Every clone of a project
  produces identical Contract Files.
- Canonical typed names only, so a Contract File does not depend on the global
  name short forms in effect in its source file.

Its contents are in a deterministic order:

- Implied qualities are sorted by canonical typed name.
- Requirements are in the order the compiler inferred them.
- Guarantees are in the order a caller must apply them (parent names before
  child names, then execution order).
- Callees are in the order this action triggered them.

The compiler produces a Contract File only for an action that compiled without
errors, so a Contract File never contains an error state.

### Callee Guarantees Are Referenced, Not Copied

A Contract File lists this action's own Guarantees and references the contracts
of the callees whose Guarantees apply after it completes. It does not copy those
callees' Guarantees into its own list.

The compiler already represents contracts this way in memory. Copying every
callee's Guarantees into every caller re-copies a callee's whole guarantee
subtree at each level of the call chain. An action call graph with fan-out F and
depth D then produces O(F^D) Guarantees, which makes compilation impossible at
scale. Referencing keeps each contract at O(own Guarantees + F references).

To learn the complete state an action leaves behind, a reader follows each
callee reference to that callee's Contract File. The callee's canonical name
gives the path of its source file, and its Contract File is next to it.

Requirements are different: the compiler already propagates them up the call
chain, so a Contract File lists every requirement the action imposes on its
callers, including those it inherited. Each inherited requirement names the
actions it propagated through.

### Schema

```proto
edition = "2024";

package define.contract;

// Top-level wrapper for .contract.defcl files.
message ContractFile {
  // The contract of the action defined in the source file.
  ActionContract contract = 1;
}

// The inferred Action Contract of one potential action.
message ActionContract {
  // Whether the Guarantees this action leaves behind can be destroyed without
  // applying them.
  enum SelfContained {
    UNSPECIFIED = 0;
    SELF_CONTAINED = 1;
    NOT_SELF_CONTAINED = 2;
  }

  // The canonical typed name of the action.
  string action = 1;

  // What triggers the action.
  Trigger trigger = 2;

  // The canonical typed names of the action's transitively implied qualities,
  // sorted.
  repeated string implied_qualities = 3;

  // The Automatic Action Requirements on occupancy, including requirements
  // propagated from callees.
  repeated OccupancyRequirement occupancy_requirements = 4;

  // The Automatic Action Requirements that a particle have a set value,
  // including requirements propagated from callees.
  repeated ValueRequirement value_requirements = 5;

  // This action's own Automatic Action Guarantees, in the order a caller
  // applies them.
  repeated Guarantee guarantees = 6;

  // The callees whose contracts a caller also applies, in trigger order.
  repeated Callee callees = 7;

  // The Destruction Contracts for caller-passed particles this action destroys.
  repeated DestructionContracts destruction_contracts = 8;

  SelfContained self_contained = 9;
}

// The Trigger Condition Statement of an action.
message Trigger {
  enum Kind {
    UNSPECIFIED = 0;
    POSITION_PRESENCE = 1;
    CONSTRUCTOR = 2;
    DESTRUCTOR = 3;
  }

  Kind kind = 1;

  // The trigger position. Set only when kind is POSITION_PRESENCE. The trigger
  // position is always assumed to be occupied, so it has no separate
  // OccupancyRequirement.
  string position = 2;
}

// An occupancy state of a position.
message Occupancy {
  enum State {
    UNSPECIFIED = 0;
    EMPTY = 1;
    OCCUPIED = 2;
  }
}

// One action that a requirement propagated through.
message PropagationStep {
  enum Kind {
    UNSPECIFIED = 0;
    // This action triggered the named action.
    ACTION_TRIGGER = 1;
    // This action destroyed a caller-passed particle, which triggered the
    // named destructor.
    DESTRUCTOR_CASCADE = 2;
  }

  Kind kind = 1;

  // The canonical typed name of the action the requirement propagated from.
  string action = 2;
}

// A requirement that a contracted position be empty or occupied.
message OccupancyRequirement {
  // The chained name of the position, from this action's perspective.
  string position = 1;

  Occupancy.State occupancy = 2;

  // The actions this requirement propagated through, from this action's direct
  // callee to the action whose statement inferred it. Empty when this action's
  // own statements inferred it.
  repeated PropagationStep propagated_through = 3;
}

// A requirement that the particle in a contracted position have a set value.
message ValueRequirement {
  // The chained name of the position, from this action's perspective.
  string position = 1;

  // As in OccupancyRequirement.
  repeated PropagationStep propagated_through = 2;
}

// An Automatic Action Guarantee about one contracted position.
message Guarantee {
  // What happened to a particle's value.
  enum ValueEffect {
    UNSPECIFIED = 0;
    UNCHANGED = 1;
    SET = 2;
    UNSET = 3;
  }

  // The chained name of the position, from this action's perspective.
  string position = 1;

  oneof state {
    // The position is empty.
    Empty empty = 2;
    // The position holds a particle that was in a contracted position when the
    // action started.
    OccupiedByExisting occupied_by_existing = 3;
    // The position holds a particle this action or one of its callees created.
    OccupiedByNew occupied_by_new = 4;
    // The action operated on the position but left it as it started.
    Unchanged unchanged = 5;
  }

  message Empty {}

  message OccupiedByExisting {
    // The contracted position the particle was in when the action started.
    string origin_position = 1;
    ValueEffect value_effect = 2;
  }

  message OccupiedByNew {
    // The canonical typed names of the particle's qualities, in assignment
    // order.
    repeated string qualities = 1;
    // The position the particle was created in.
    string origin_position = 2;
    ValueEffect value_effect = 3;
  }

  message Unchanged {}
}

// A callee whose contract a caller applies after this action's own Guarantees
// are known.
message Callee {
  // The chained name of the callee from this action's perspective, ending in
  // the callee's action name.
  string action_chain = 1;
}

// Destruction Contracts for particles destroyed in one Simultaneous Transitive
// Destruction, which share one Child State.
message DestructionContracts {
  repeated DestroyedParticle particles = 1;

  // The Child State: what is known about the destroyed particles' transitive
  // child positions immediately before destruction.
  repeated ChildPositionState child_state = 2;

  // The actions this destruction propagated through, from this action's direct
  // callee to the destroying action. Empty when this action destroyed the
  // particles itself.
  repeated PropagationStep propagated_through = 3;
}

// The Destruction Fact for one destroyed particle, and the destructors already
// verified for it.
message DestroyedParticle {
  enum Destruction {
    UNSPECIFIED = 0;
    EXPLICIT = 1;
    AUTOMATIC = 2;
  }

  // The contracted position the particle was in, from this action's
  // perspective.
  string contracted_position = 1;

  // The canonical typed name of the action that destroyed the particle.
  string destroying_action = 2;

  Destruction destruction = 3;

  // The position the destroying action destroyed directly, from the destroying
  // action's perspective.
  string directly_destroyed_position = 4;

  // This particle's position, from the destroying action's perspective.
  string destroyed_position_in_destroyer = 5;

  // This particle's position relative to the Child State. Empty when this
  // particle is the one the Child State describes.
  string position_in_child_state = 6;

  // The canonical typed names of destructors already verified for this
  // particle.
  repeated string verified_destructors = 7;
}

// What is known about one child position at destruction time.
message ChildPositionState {
  enum Value {
    UNSPECIFIED = 0;
    SET = 1;
    UNSET = 2;
  }

  // The chained name of the child position, relative to the destroyed
  // particle.
  string position = 1;

  Occupancy.State occupancy = 2;

  // UNSPECIFIED when the value state is not known.
  Value value = 3;
}
```

## A Real Program

A TCP handshake. Each state is a position, and each transition moves the
connection's particle from one state position to another.

`transitions/listen_recv_syn.dfn`:

```define
define the potential action<mv:example.com:tcp:/transitions/listen_recv_syn> {
    it also assigns the position</states/listen>.
    it also assigns the position</states/syn_received>.

    define the position<run>.

    it happens when {
        the position<run> has a particle.
    } and it does {
        move the particle in position</states/listen> to position</states/syn_received>.
        destroy the particle in position<run>.
    }
}
```

`transitions/syn_received_recv_ack.dfn` is the same shape, moving the particle
from `position</states/syn_received>` to `position</states/established>`.

`handshake.dfn`:

```define
define the potential action<mv:example.com:tcp:/handshake> {
    it also assigns the action</transitions/listen_recv_syn>.
    it also assigns the action</transitions/syn_received_recv_ack>.

    define the position<run>.

    it happens when {
        the position<run> has a particle.
    } and it does {
        create a particle in action</transitions/listen_recv_syn>::position<run>.
        create a particle in action</transitions/syn_received_recv_ack>::position<run>.
        destroy the particle in position<run>.
    }
}
```

Nothing in `handshake.dfn` says that triggering it requires the connection's
particle to be in `position</states/listen>`. `handshake` cannot even write that
name, because `position</states/listen>` is implied only transitively, through
`action</transitions/listen_recv_syn>`.

`handshake.contract.defcl` shows it:

```
# Contract of action<mv:example.com:tcp:/handshake>, inferred by the Define
# compiler from handshake.dfn. Do not edit. Regenerate with: <command>
contract: {
    action: "action<mv:example.com:tcp:/handshake>"
    trigger: {
        kind: POSITION_PRESENCE
        position: "position<run>"
    }
    implied_qualities: [
        "action<mv:example.com:tcp:/transitions/listen_recv_syn>",
        "action<mv:example.com:tcp:/transitions/syn_received_recv_ack>",
        "position<mv:example.com:tcp:/states/established>",
        "position<mv:example.com:tcp:/states/listen>",
        "position<mv:example.com:tcp:/states/syn_received>"
    ]
    occupancy_requirements: [
        {
            position: "position<mv:example.com:tcp:/states/listen>"
            occupancy: OCCUPIED
            propagated_through: [
                {
                    kind: ACTION_TRIGGER
                    action: "action<mv:example.com:tcp:/transitions/listen_recv_syn>"
                }
            ]
        },
        {
            position: "position<mv:example.com:tcp:/states/syn_received>"
            occupancy: EMPTY
            propagated_through: [
                {
                    kind: ACTION_TRIGGER
                    action: "action<mv:example.com:tcp:/transitions/listen_recv_syn>"
                }
            ]
        },
        {
            position: "position<mv:example.com:tcp:/states/established>"
            occupancy: EMPTY
            propagated_through: [
                {
                    kind: ACTION_TRIGGER
                    action: "action<mv:example.com:tcp:/transitions/syn_received_recv_ack>"
                }
            ]
        }
    ]
    guarantees: [
        {
            position: "position<mv:example.com:tcp:/states/established>"
            occupied_by_existing: {
                origin_position: "position<mv:example.com:tcp:/states/listen>"
                value_effect: UNCHANGED
            }
        },
        {
            position: "position<run>"
            empty: {}
        }
    ]
    callees: [
        { action_chain: "action<mv:example.com:tcp:/transitions/listen_recv_syn>" },
        { action_chain: "action<mv:example.com:tcp:/transitions/syn_received_recv_ack>" }
    ]
    destruction_contracts: [
        {
            particles: [
                {
                    contracted_position: "position<run>"
                    destroying_action: "action<mv:example.com:tcp:/handshake>"
                    destruction: EXPLICIT
                    directly_destroyed_position: "position<run>"
                    destroyed_position_in_destroyer: "position<run>"
                }
            ]
        }
    ]
    self_contained: NOT_SELF_CONTAINED
}
```

The contracts above are what the compiler infers today for this program. The
Guarantees that `position</states/listen>` and `position</states/syn_received>`
end up empty are in the callees' Contract Files, which a reader reaches through
`callees`.

## Why This is the Right Solution

- **It keeps DLP 37's inference.** The logic of a contract stays in one place,
  the Action Statements Block, and interface positions and implied qualities
  still work the same way for the programmer.
- **It makes inferred contracts visible without new syntax**, including the
  transitive requirements that no declaration syntax could express.
- **Agents find it the way they find everything else**: by listing a directory
  and reading a file next to the source they are working on. Textproto is common
  in public code, so agents read defcl without learning anything new.
- **One schema, two forms.** The text and binary forms cannot drift apart, and
  converting between them comes with protocol buffers.
- **It gives the compiler an intermediate representation** that makes
  incremental compilation and build-system early cutoff possible, where most
  edits change a body but not its contract.
- **It is safe to share.** The text form is never trusted by the compiler, and
  the binary form is never checked in, so a hand-edited or stale Contract File
  cannot make the compiler accept an invalid program.
- **Contract changes appear in code review.** A change to a callee that changes
  its contract, or its callers' inherited requirements, changes the checked-in
  Contract Files.

Alternatives considered:

- **Explicit contract syntax.** It cannot express transitive requirements on
  implied qualities (problem 2), so it would apply to interface positions but
  not to implied qualities.
- **A checked-in build cache.** Recording an input key (the source digest, the
  direct callees' contract digests, and the compiler identity) in each text
  Contract File would let a fresh clone skip inference. It adds a key block to
  every file, changes the file on every source edit, and requires the compiler
  to trust checked-in files. We will reconsider it if full inference in a fresh
  clone is measurably slow.
- **Checking in the binary form.** Reviewers cannot read what the compiler
  trusts, it doubles the number of files in the tree, and it would require a
  byte-level canonical encoding.

## Forward Compatibility

The schema evolves under the protocol buffers rules that DCL already mandates.
New fields and enum values can be added without breaking existing Contract
Files, and old enum names are never removed.

Every state in the schema is an enum, not a boolean, so it can grow. For
example, branching will need occupancy and value states that depend on which
branch ran, and DLP 53 calls for value Guarantees that record an exact value or
the strictest known constraints.

Contract Files are fully derived from source, so any schema change is deployed
by regenerating them.

## Refactoring Existing Systems

This proposal changes no Define syntax. Existing projects adopt it by running
the compiler once to generate their text Contract Files and checking them in.

## Open Questions

1. **Source locations for diagnostics.** Requirement propagation errors show the
   source location of each step in the chain. Contract Files contain no
   locations, so a caller's diagnostics cannot show locations inside its
   callees. One option is to record each step as a statement index within the
   Action Statements Block, which changes only when statements are added or
   removed, and map it to a line only when rendering a diagnostic.
2. **DCL's scope.** The DCL spec describes DCL as the language for configuration
   files in the `.define` directory, and says not to use it as a storage format.
   The text form is a generated, human-readable view that nothing reads back,
   which is arguably neither, but the DCL spec needs a proposal that covers this
   use.
3. **Compiler-only facts.** `self_contained` exists only so callers can skip
   work. It could stay in the schema, but agents and people have no use for it
   in the text form.
4. **Destruction Contracts.** The `DestructionContracts` and `DestroyedParticle`
   messages mirror the compiler's current in-memory types field for field. They
   need review to confirm every field is part of the contract rather than an
   implementation detail.
5. **Constructor and destructor assignments in propagation chains.** The
   compiler records the constructor or destructor assignment that caused some
   requirements to propagate, for use in diagnostics. `PropagationStep` does not
   include it yet.
6. **Writing into the source tree under Bazel.** Bazel actions cannot write to
   the source tree, so generating the text form needs a `bazel run` target, the
   way formatting does today.
